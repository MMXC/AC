# Requirement Clarifier

通过交互式对话澄清用户需求，明确具体要求，识别优化方向，并生成符合 `requirement-workflow.sh` 可处理的任务格式。

## 核心功能

1. **需求澄清**：通过对话明确用户的具体要求
2. **优化识别**：识别可能的优化方向（性能、用户体验、可维护性等）
3. **任务生成**：生成符合 requirement-workflow.sh 格式的 JSON 任务列表
4. **用户确认**：询问用户是否添加优化项
5. **工作流衔接**：在需求与任务确认后，引导或直接触发 `requirement-workflow.sh` 进行后续 backlog 创建与 Ralph 执行

## 使用场景

**Trigger**:
- "根据这个需求生成任务: <粗略描述>"
- "帮我澄清这个需求: <描述>"
- "将这个需求转换为任务格式: <描述>"
- 用户提供粗略或不完整的需求描述

## 工作流程

### 阶段 1: 需求理解与澄清

1. **分析初始需求**
   - 识别需求类型（Web 应用、CLI 工具、API、库等）
   - 提取关键功能点
   - 识别技术栈线索

2. **主动澄清关键问题**
   - **技术栈**：使用的编程语言、框架、库
   - **功能范围**：核心功能 vs 可选功能
   - **约束条件**：性能要求、兼容性、安全要求
   - **用户场景**：目标用户、使用环境
   - **数据存储**：是否需要持久化、数据格式

3. **等待用户回答并更新需求理解**

### 阶段 2: 优化方向识别

识别可能的优化方向，包括但不限于：

- **性能优化**：缓存、懒加载、代码分割、数据库优化
- **用户体验**：错误提示、加载状态、响应式设计、无障碍支持
- **代码质量**：类型检查、单元测试、代码规范、文档
- **安全性**：输入验证、身份认证、数据加密、XSS/CSRF 防护
- **可维护性**：模块化设计、配置管理、日志记录、错误处理
- **可扩展性**：插件系统、API 设计、架构模式

### 阶段 3: 优化建议展示

展示识别到的优化方向：

```markdown
## 识别到的优化方向

### 性能优化
- [ ] 添加缓存机制
- [ ] 实现懒加载
- [ ] 代码分割优化

### 用户体验
- [ ] 添加加载状态提示
- [ ] 优化错误提示信息
- [ ] 响应式设计支持

### 代码质量
- [ ] 添加单元测试
- [ ] TypeScript 类型检查
- [ ] 代码规范检查
```

询问用户："是否将这些优化项添加到任务列表中？"

### 阶段 4: 任务生成

基于澄清后的需求和用户选择的优化项，生成符合格式的任务列表。

## 任务格式规范

生成的任务必须符合 `requirement-workflow.sh` 期望的 JSON 格式：

```json
{
  "id": "task-001",
  "title": "任务标题",
  "description": "详细的任务描述",
  "test_command": "可执行的测试命令",
  "success_criteria": [
    "成功标准 1",
    "成功标准 2"
  ],
  "test_cases": {
    "test_data": [
      {
        "input": "输入数据",
        "expected_output": "预期输出"
      }
    ],
    "test_scenarios": [
      "测试场景描述 1",
      "测试场景描述 2"
    ],
    "assertions": [
      "断言示例 1",
      "断言示例 2"
    ]
  },
  "dependencies": []
}
```

### 字段说明

- **id**: 唯一任务标识符，格式如 `task-001`, `backend-001`
- **title**: 简洁明确的任务标题
- **description**: 详细描述，包含实现要点
- **test_command**: 可执行的测试命令，用于验证任务完成
- **success_criteria**: 成功标准列表，每个标准应该是可验证的
- **test_cases**: 测试用例（可选但推荐）
  - `test_data`: 输入输出测试数据
  - `test_scenarios`: 测试场景描述
  - `assertions`: 断言示例
- **dependencies**: 依赖的其他任务 ID 列表（尽量保持为空，确保正交性）

## 分解原则

遵循与 `requirement-decomposer` 相同的原则：

### 正交性（Orthogonality）
- 任务之间相互独立
- 可以并行执行
- 无依赖关系

### 原子性（Atomicity）
- 每个任务不可再分
- 有明确的输入输出
- 有明确的完成标准

### 可测试性（Testability）
- 每个任务必须有明确的测试命令
- 测试结果二元化（通过/失败）
- 可自动化执行

## 对话策略

### 澄清问题示例

**技术栈相关**：
- "这个项目使用什么技术栈？(TypeScript/JavaScript/Python/其他)"
- "是否需要使用特定的框架或库？"

**功能相关**：
- "这个功能的核心流程是什么？"
- "有哪些边界情况需要处理？"
- "是否需要支持多种输入格式？"

**性能相关**：
- "预期的用户规模是多少？"
- "是否有性能要求？(响应时间、并发数等)"
- "数据量级大概是多少？"

**用户体验相关**：
- "目标用户是谁？"
- "是否需要支持移动端？"
- "错误提示需要多详细？"

### 优化建议展示格式

```markdown
## 💡 优化建议

基于您的需求，我识别到以下可能的优化方向：

### 🚀 性能优化
1. **添加缓存机制** - 减少重复计算，提升响应速度
2. **实现懒加载** - 按需加载资源，优化初始加载时间

### 🎨 用户体验
1. **添加加载状态** - 提升用户等待体验
2. **优化错误提示** - 提供更友好的错误信息

### 🔒 安全性
1. **输入验证** - 防止恶意输入
2. **XSS 防护** - 防止跨站脚本攻击

**是否将这些优化项添加到任务列表中？** (Y/n)
```

## 输出格式

最终输出应该包括：

1. **澄清后的需求总结**
2. **任务列表预览**（Markdown 格式，便于用户审查）
3. **JSON 格式任务列表**（供 requirement-workflow.sh 使用）

### 阶段 5: 触发 requirement-workflow 工作流

当：
- 需求已澄清完毕，且
- 任务列表（含可选优化项）已经由用户确认无误

时，**应显式询问用户**是否要继续进入自动化需求工作流：

- 提示文案示例：
  - 「是否现在就用 `requirement-workflow.sh` 创建 backlog 任务并（可选）交给 Ralph 执行？(Y/n)」

如果用户选择 **是**，按照以下原则处理：

1. **优先利用澄清后的最终需求描述**  
   - 构造一段「最终版需求说明」文本（包含已确定的范围与约束）  
   - 建议命令示例（供用户或 Agent 执行）：

   ```bash
   # 在项目根目录下
   ./.cursor/ralph-scripts/requirement-workflow.sh "【这里替换为澄清后的最终需求描述】"
   ```

2. **也可以让用户使用交互模式**（更适合不想手写长命令时）：

   ```bash
   ./.cursor/ralph-scripts/requirement-workflow.sh --interactive
   ```

3. **如果 Agent 具备执行 Shell 的能力**：  
   - 在用户明确同意后，可以直接代表用户执行上述命令  
   - 执行前再次简短复述：将要传入 requirement-workflow.sh 的需求概要，确保用户心中有数  

4. **如果用户只想先生成任务、不立刻创建 backlog**：  
   - 只输出 JSON / Markdown 任务列表  
   - 明确提示「稍后可以手动运行 `requirement-workflow.sh` 并粘贴/重述这份需求描述」  

整体目标：**clarifier 负责把「需求 & 优化」想清楚，requirement-workflow 负责把这些需求落进 backlog 并衔接 Ralph**，两者衔接的时机和是否执行，始终由用户最后一拍板。

### 推荐的脚本化调用模式

在决定触发 `requirement-workflow.sh` 时，可以根据场景选择不同的参数组合，并在对话里给出「推荐命令」：

- **安全、默认推荐（带人工确认）**  
  适用于：第一次使用 / 需求比较大 / 想再看一遍任务列表。  
  - 推荐命令：

  ```bash
  ./.cursor/ralph-scripts/requirement-workflow.sh "【澄清后的最终需求描述】"
  ```

  - 行为：  
    - 内部会先分解需求  
    - 展示分解结果  
    - 再询问是否创建 backlog 任务  

- **批量、高频使用时的快捷模式：`--no-confirm`**  
  适用于：  
  - 需求已经非常清晰，  
  - 且刚刚用 clarifier 做过一轮对话确认，  
  - 不希望再在命令行里多点一次确认。  

  - 推荐命令：

  ```bash
  ./.cursor/ralph-scripts/requirement-workflow.sh --no-confirm "【澄清后的最终需求描述】"
  ```

  - 提醒 Agent：  
    - 在建议/执行 `--no-confirm` 前，要再次**简短复述**将要创建的任务范围，确保用户知道这是「不再弹确认」的快速通道。  

- **一条龙自动执行：`--no-confirm --auto-execute`**  
  适用于：  
  - 小型、单人项目，  
  - 用户希望「想完就立刻开干」，  
  - 对 Ralph 执行流程比较熟悉。  

  - 推荐命令：

  ```bash
  ./.cursor/ralph-scripts/requirement-workflow.sh --no-confirm --auto-execute "【澄清后的最终需求描述】"
  ```

  - 行为：  
    - 跳过 requirement-workflow 内部的确认  
    - 直接创建 backlog 任务  
    - 并立刻进入 Ralph 执行第一个任务的流程  

  - 使用前提（Agent 要在对话里明确点出）：  
    - 用户已经看过/接受当前这一批任务的拆分结果  
    - 接受「直接创建并立即执行」这一行为  

- **交互补充模式：`--interactive`**  
  如果澄清过程中发现还有零星信息不方便在一句命令里写全，也可以建议用户使用交互模式，让脚本进一步提问：

  ```bash
  ./.cursor/ralph-scripts/requirement-workflow.sh --interactive
  ```

总结：  
- **默认用「无参数版本」**，保持可见的二次确认；  
- **熟练用户在明确同意后，可以引导使用 `--no-confirm` / `--auto-execute`** 提升流畅度；  
- clarifier 在文案上要始终帮用户意识到：这些 flag 是「省事」，但前提是「需求和拆分已经足够可信」。

**用户**: "创建一个待办事项应用"

**Agent**: 
```

1. **技术栈**：您希望使用什么技术栈？
   - TypeScript/JavaScript
   - Python
   - 其他

2. **功能范围**：需要哪些核心功能？
   - 添加/删除/完成待办事项
   - 是否需要分类/标签
   - 是否需要优先级
   - 是否需要截止日期

3. **数据存储**：数据如何存储？
   - 本地文件（JSON）
   - 数据库
   - 浏览器 localStorage

4. **界面类型**：需要什么类型的界面？
   - CLI 命令行工具
   - Web 应用
   - 桌面应用
```

**用户**: "TypeScript CLI 工具，支持 add/list/done，用 JSON 文件存储"

**Agent**:
```
好的，需求已明确：
- 技术栈：TypeScript CLI
- 功能：add/list/done 命令
- 存储：JSON 文件

## 💡 优化建议

基于您的需求，我识别到以下可能的优化方向：

### 🎨 用户体验
1. **帮助信息** - 添加 --help 参数，显示使用说明
2. **错误处理** - 友好的错误提示信息

### 🔒 代码质量
1. **TypeScript 类型检查** - 确保类型安全
2. **单元测试** - 添加测试用例确保功能正确

### 📝 文档
1. **README** - 添加使用说明文档

**是否将这些优化项添加到任务列表中？** (Y/n)
```

## 最佳实践

1. **主动澄清**：不要假设，主动询问关键信息
2. **渐进式澄清**：先问最关键的问题，再问细节
3. **优化建议要具体**：每个优化项应该有明确的实现目标
4. **保持正交性**：确保生成的任务可以并行执行
5. **测试命令要可执行**：确保测试命令可以直接运行验证
6. **用户确认**：在生成最终任务前，展示预览供用户审查

## 与 requirement-decomposer 的区别

- **requirement-decomposer**: 直接分解已明确的需求，输出任务列表
- **requirement-clarifier**: 先通过对话澄清需求，识别优化方向，再生成任务列表

两者可以配合使用：先用 clarifier 澄清需求，再用 decomposer 分解为子任务。
